## 0 一句话

用户能把 SillyTavern 的世界书文件（World Info / Lorebook 的 JSON）导入进一个“世界书仓库”（也能新建、能改条目），挂到剧本上；开新故事时，剧本里各张卡自带的世界书和挂上的世界书合成一份，跟着这一局存下来；之后每回合**按 SillyTavern 的规则**挑出该出现的条目，把原文带给导演。

名词先说清楚：

- **世界书**：一组设定条目。每条有标题、几个关键词和一段内容，例如标题“青石渡”、关键词“青石渡、渡口”、内容是这个渡口的样子和规矩。
- **触发**：故事里出现了某条的关键词，这条的内容就放进导演这一回合的上下文。
- **常驻条目**：不看关键词、每回合都放进去的条目（写世界的大背景用）。
- **递归**：被触发的条目的内容里又出现了别的条目的关键词，那一条也跟着触发。

## 1 做之前的情况

### 1.1 我们（2026-10-25 以前）

- 只有**角色卡里自带的世界书**（卡的 `book`，`domain/scenario/card.py` 的 `LoreEntry`：标题、关键词、内容、常驻、启用、先后）。导入角色卡时次要关键词、匹配逻辑、递归、分组、概率这些设置都丢掉了。工作台的手动表单（网页和 App 的 `BookEditor`，逻辑在 `packages/core/src/scenario/cardEdit.ts`）能改它。
- **普通模式**：开局时 WorldBuilder 读几张卡合在一起的世界书，常驻的优先，最多 40 条、12000 字，让模型提炼进世界状态（人物、地点、事实）。**之后再也不看世界书**：条目原文不进上下文，40 条以外的条目没用上。
- **闪电模式**：开局时把卡的原文连同世界书存成快照（`domain/world/card_source.py`），整段放进导演的系统提示，整份最多 15000 字，超了先丢不常驻的条目。不看关键词，全放。
- 不能导入单独的世界书文件，也不能挂到剧本上。

### 1.2 SillyTavern 怎么做（本机 `~/Developer/SillyTavern`，2026-09-14 那一版）

下面的“默认”指新装 ST 时的设置（`default/content/settings.json`），不是代码里变量的初始值，两者有几处不一样（递归、整词匹配），以新装设置为准，因为用户拿到的就是它。

**文件**：`data/<用户>/worlds/<书名>.json`，书名就是文件名。内容是 `{ "entries": { "0": {…}, "1": {…} } }`，条目按 `uid` 存成对象；从角色卡里导出来的还带一个 `originalData`。每条的字段见 `public/scripts/world-info.js` 的 `newWorldInfoEntryDefinition`，第 6 节逐个对照。

**挂在哪**（`getSortedEntries`）：全局、角色（卡绑一本主书，再加几本额外的）、聊天、人设四处。合并时聊天的在最前，然后人设，然后角色和全局（默认“角色优先”：角色挂的几本混在一起按 `order` 从大到小排，再接全局的）。同一本挂在几处只算一次。卡里内嵌的世界书 ST 不直接用，要先“导入卡里的世界书”转成独立的一本、绑到角色上。

**每回合怎么挑**（`checkWorldInfo`，每次生成前跑一遍）：

1. **扫哪些文字**：最近 2 条消息，也就是用户刚发的这条和上一条回复（`world_info_depth: 2`）。**每条前面带说话人的名字**（`world_info_include_names: true`，写成“沈知微: ……”），所以关键词是角色名或用户名的条目几乎每次都触发。条目可以自己改扫几条（`scanDepth`），也可以勾上“顺带扫角色描述、性格、场景、作者备注、人设描述”。
2. **怎么算命中**：不区分大小写（`world_info_case_sensitive: false`）；**按整词匹配**（`world_info_match_whole_words: true`）：一个词的关键词前后不能紧挨着英文字母、数字或下划线，所以英文的 `art` 不会命中 `start`；中文前后都不是这几种字符，实际效果就是按包含找；关键词里有空格时直接按包含找。关键词可以写成正则 `/……/i`，正则按原文匹配。关键词里的 `{{char}}` 这类宏先替换。
3. **一条条判断**（按优先级从高到低）：停用的跳过；“只在某种生成方式下触发”（`triggers`）对不上的跳过；还在冷却、还没到延迟的跳过；常驻的、还在粘滞期的直接算；否则主关键词命中任一个，再按次要关键词的逻辑判断（再命中任一个 / 全命中 / 一个都不命中 / 不全命中）。
4. **同组只留一条**：这一轮命中的条目里，同一个组（`group`，可以写几个组）的只留一条：已经有同组的进来了就全不要；有“组内优先”的取 `order` 最大的；开了组打分的先留命中关键词最多的；剩下的按权重（`groupWeight`）随机抽一条。
5. **掷概率、装预算**：按优先级一条条来，设了概率的掷一次，没掷中这次就不要；装进去的内容加起来超过预算就停（预算默认是上下文长度的 25%，不设上限；“不占预算”的条目照样进）。
6. **递归**（新装默认开，`world_info_recursive: true`，不限轮数）：这一轮装进去的条目（“内容不去触发别的”的除外）的内容加进要扫的文字，再扫一轮，直到没有新条目或预算满了；“不被递归触发”的条目只在第一轮能进；“只在递归时触发”的条目只在递归的轮次里能进（可以写第几层；第一层一开始就算轮到，没有新条目时，还有更高的层没轮到就按下一层多扫一轮，即使递归关着也是）。
7. **粘滞、冷却、延迟**（按消息条数算，记在聊天的元数据里）：触发后连着生效几条消息、之后冷却几条不能再触发、聊天满几条以后才能触发。
8. **放进提示词**：**只放内容，不放标题**（标题是给人看的备注）。按 `order` 从小到大排，`order` 越大越靠后。按每条的“位置”分别插到角色设定前（默认）或后、作者注释上下、对话示例上下、聊天记录倒数第几条（可以指定是系统、用户还是助手说的）、宏占位。

## 3 放在哪、怎么合并

### 3.1 为什么是“仓库 + 剧本引用”

- **挂在剧本上**（世界书是剧本的一部分）：简单，但一本世界观书要给好几个剧本用时，每个剧本各导一份。
- **独立的世界书仓库，剧本引用**：一本书给多个剧本用；和现在“角色卡仓库 + 剧本引用卡”的结构一样。ST 用户的习惯也是一本书挂给好几个角色。

选第二种。ST 的全局、聊天、人设三种挂法不做（第 8.3 节）。

### 3.2 开新故事时合成一份

开局搭世界时（WorldBuilder 之前），把这几处的条目放在一起：主角色卡的世界书、其余几张卡的世界书（按剧本里卡的顺序）、剧本挂的世界书（按挂的顺序）。在 ST 里这相当于“角色挂的几本书”，几本混在一起按优先级数字排（3.3）。

- 停用的、没有内容的条目不要。
- 宏在这时替换：`{{user}}` 换成主角名；`{{char}}` 在卡的书里换成那张卡的角色名，在挂的书里换成主角色卡的角色名。关键词里的宏也换。其他宏删掉（第 8.2 节）。
- 标题和内容都一样的条目只留第一条（同一本书既在卡里又单独导入过时会出现）。
- 勾了“顺带扫角色描述”等的条目要用到卡的描述、性格、场景、作者备注和主角介绍，这几段文字也一起存进快照（宏同样替换好）。
- 整份最多 3000 条、60 万字，超出时从最后一本书的末尾往前丢，记一条 `world.lore_truncated` 警告。

合成的这一份存进这一局（新表 `playthrough_lore`，第 4 节），之后改卡、改书、换书都不影响这一局，和卡的原文快照一样。这个功能上线前开局的存档没有这一份，照旧没有世界书。

### 3.3 先后和优先级

ST 每条有一个 `order` 数字，既管优先级、也管在提示词里的先后，而且是拿这个数字在几本书之间比较的。我们的条目已经有一个 `order`，意思是“在列表里排第几”（工作台保存时按列表重新编号），所以**另加一个 `priority`** 存 ST 的那个数字，两者分开：

- `order`：列表里的位置，只管显示和编辑时的先后。导入 ST 世界书时按文件里的顺序（`displayIndex`，没有就按 `uid`）。
- `priority`：ST 的 `order` 原样存下（导入卡时取 `insertion_order`，ST 也是这么对应的）。编辑页的“更多设置”里能改，新建的条目是 100（ST 的默认）。工作台调整列表先后不动它。以前导入的卡没有这个字段，按 `order` 算。
- 优先级：`priority` 大的先挑、先装进预算；一样大的按合并时的先后。和 ST“角色挂的几本混在一起按 `order` 从大到小排”一样。
- 放进上下文的顺序：`priority` 从小到大，大的靠后（离生成点更近），和 ST 一样。
- 导出角色卡时 `insertion_order` 写 `priority`（以前写的是列表序号）。
- WorldBuilder 挑那 40 条时以前是 `order` 小的优先，改成了同一个规则（常驻的仍然最优先，其次 `priority` 大的）。

## 4 数据表

迁移 0025（仓库和剧本引用）、0026（这一局的快照）、0027（每回合的记录 `turns.lore`）。下面是设计时的考虑；实际的列、约束和索引以 [data-model/library.md](data-model/library.md)、[data-model/story.md](data-model/story.md) 为准。

### `lorebooks`（新）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | uuid | 主键 |
| `user_id` | uuid | → `users.id`，级联删除 |
| `name` | text | 书名，最多 80 字。导入时取文件里的名字（`originalData.name`、`name`），没有就用文件名 |
| `description` | text | 简介，最多 2000 字，可以为空 |
| `source` | text | `st_world`（ST 的世界书文件）/ `lorebook`（角色卡规范里单独导出的世界书）/ `manual`（在 BetterTavern 里新建的） |
| `source_sha256` | text | 导入文件的 SHA-256，同一个用户同一个文件只记一本（同角色卡）；另外导入的那份为空 |
| `raw` | jsonb | 导入时的原始 JSON，原样保存；以后导出、补做新特性时用 |
| `book` | jsonb | 规范化的条目数组，结构同卡的 `book`（第 6.1 节） |
| `report` | jsonb | 导入报告（第 6.3 节） |
| `version` | integer | 改名、改简介、改条目时加 1；改的时候带着读到的版本号，对不上返回 409 |
| `created_at`、`updated_at` | timestamptz | |

约束与索引：`lorebooks_user_idx (user_id, updated_at DESC)`；`lorebooks_user_sha_uq (user_id, source_sha256) WHERE source_sha256 IS NOT NULL`。每个用户最多 100 本（`Quotas.max_lorebooks`，超了 409 `TOO_MANY_LOREBOOKS`）。

### `scenario_lorebooks`（新）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `scenario_id` | uuid | → `scenarios.id`，级联删除 |
| `lorebook_id` | uuid | → `lorebooks.id`，**级联删除**：删书时自动从剧本里摘掉 |
| `position` | smallint | 第几本，0 到 3（一个剧本最多 4 本） |

主键 `(scenario_id, lorebook_id)`，`(scenario_id, position)` 唯一，`(lorebook_id)` 索引。换书时整个替换，和 `scenario_cards` 一样。卡被剧本用着时不能删（剧本没卡就不成立），书被用着时可以删，剧本少一本书照样能玩；删之前客户端提示“N 个剧本在用”。

### `playthrough_lore`（新）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `playthrough_id` | uuid | 主键，→ `playthroughs.id`，级联删除 |
| `entries` | jsonb | 合成好的条目（宏已替换），每条多记一个来源：`{"kind": "card" / "book", "name": "…"}` |
| `meta` | jsonb | 合了哪几本、丢了几条；“顺带扫描”要用的几段文字（卡的描述等、主角介绍） |
| `created_at` | timestamptz | |

开局时和世界状态在同一个事务里写入。不放进 `playthroughs.seed`：世界书可能有几十万字，存档列表等别的地方读 `playthroughs` 时不该把它带出来。

### `turns.lore`（新列）

jsonb，默认 `'{}'`。导演写完这一回合时，在提交回合的同一个事务里写下：这一回合挑中了哪几条（在快照里的序号），以及写完以后哪些条目还在粘滞期、冷却期、各到第几回合结束。下一回合只读上一回合（活跃链上的父回合）的这一列，就知道粘滞和冷却的状态。

这样不用在别处记状态：回退到第 K 回合时，第 K 回合之后的回合被撤销，下一回合读的就是第 K 回合的记录，粘滞和冷却自然跟着回去。

## 5 接口

都在 `/v1` 下，请求和响应的字段以 [api/library.md](api/library.md) 的“世界书仓库”一节为准。

| 接口 | 说明 |
| --- | --- |
| `GET /v1/lorebooks` | 我的世界书，按最近修改倒序。每项：id、书名、简介、条目数、常驻条数、来源、几个剧本在用、导入报告、时间（不带条目全文） |
| `POST /v1/lorebooks/import` | multipart：`file`（JSON，最大 8 MB）、`allow_duplicate`。成功 201 返回详情（含导入报告）；同一个文件导入过、又没让另起一份时返回 200 和已有的那本（同导入角色卡）。和工作台的导入共用每分钟 20 次的计数 |
| `POST /v1/lorebooks` | 新建一本空白的世界书（书名必填），`source` 是 `manual` |
| `GET /v1/lorebooks/{id}` | 详情：概况、全部条目、导入报告、在用的剧本 |
| `PATCH /v1/lorebooks/{id}` | 改书名、简介；带 `version` 时检查有没有在别处改过（409 `LOREBOOK_CHANGED`） |
| `PUT /v1/lorebooks/{id}/book` | 编辑条目的自动保存：整本的条目（不是只传改了的）和读到的 `version`，版本号加 1；对不上 409 `LOREBOOK_CHANGED`，客户端重新读取再改。和工作台草稿的自动保存一样宽松：标题、正文、关键词可以暂时空着（这样的条目不会被带上，编辑页标出来）；超过上限的拒绝（422 `VALIDATION_ERROR`，带出错的字段，比如 `book.3.content`），不截断。请求体最大 8 MB |
| `DELETE /v1/lorebooks/{id}` | 删除，从挂着它的剧本里摘掉；已经开始的故事不受影响。204 |
| 剧本接口 | `ScenarioIn`、`ScenarioPatchIn` 加 `lorebook_ids`（0 到 4 本，按顺序，重复的算一次）；`ScenarioOut` 加 `lorebooks`（`[{lorebook_id, name, entries}]`）。换书时剧本版本号加 1；书不存在 404 |

新错误码（写进 [api/README.md](api/README.md)，客户端按码翻译）：

| HTTP | code | 情形 |
| --- | --- | --- |
| 422 | `LOREBOOK_INVALID` | 不是世界书、JSON 坏了、嵌套太深、一条有内容的条目都没有、文字总量超过 50 万字 |
| 422 | `LOREBOOK_IS_CARD` | 传的是角色卡（客户端提示去工作台导入） |
| 409 | `TOO_MANY_LOREBOOKS` | 到 100 本了，带 `limit` |
| 409 | `LOREBOOK_CHANGED` | 改的时候版本号对不上 |

## 6 导入时字段怎么映射

代码在 `importers/lorebook/`（按约定只 import `domain`），格式按内容识别，不看扩展名：

1. **ST 世界书文件**：顶层有 `entries`（对象或数组），条目里有 `key` 或 `content`；
2. **角色卡规范里的独立世界书**：`{"spec": "lorebook_v3", "data": {…}}`，或者直接就是一个 `character_book`（`entries` 数组，条目里是 `keys`、`insertion_order`，ST 的设置在每条的 `extensions` 里）。Chub 等网站导出的就是这种；
3. **角色卡**：拒绝，返回 `LOREBOOK_IS_CARD`；
4. 其他（NovelAI、Agnai、RisuAI 的格式）：先不认，返回 `LOREBOOK_INVALID`（ST 里各有一个转换函数，以后照着加）。

### 6.1 条目多存的字段

`LoreEntry` 加下面这些字段，卡里的世界书和独立世界书共用。不常用的放进一个子对象 `rules`，没设的取 ST 新装时的默认值：

| 字段 | 默认 | 意思 |
| --- | --- | --- |
| `priority` | 空（按 `order` 算） | ST 的 `order` 数字：优先级和在上下文里的先后（3.3） |
| `secondary_keys` | 空 | 次要关键词 |

## 7 运行时怎么挑条目

逐步照着 1.2 的第 1–7 步做，都是纯函数、能单测：开局合成快照在 `domain/world/lore.py`（只用标准库和 pydantic）；每回合挑条目在 `runtime/context/lore.py`（门面，`select_lore`），关键词、正则和超时在同级的 `lore_match.py`，概率、粘滞冷却延迟、分组在 `lore_effects.py`。正则要用 `regex` 库，按分层约定 `domain` 不引入它，所以挑选放在 `runtime`。

### 7.1 扫哪些文字

- 默认最近 2 条消息：**玩家这一回合的行动**和**上一段叙述**，和 ST 一样**前面带名字**：行动前面是主角名，叙述前面是主角色卡的角色名（写成“林川: ……”“沈知微: ……”）。这样关键词是角色名、主角名的条目也会像在 ST 里一样几乎每回合都触发。
- 开场那一回合：扫选定的开场白（前面带主角色名）和开场简报（地点、在场人物、情境、钩子）。写结局那一回合：结局方向和上一段叙述。
- 条目设了扫描深度的往回多看几条：一回合是两条消息（行动、叙述），从上下文里本来就有的原文回合里取（当前这一章加上一章最后两回合），再早的不看。
- 勾了“顺带扫描”的条目，扫描文字加上快照里存的对应那几段。

### 7.2 怎么算命中

和 ST 一样：

- 普通关键词：文字和关键词都转小写（区分大小写的条目不转）；整词匹配的、关键词里没有空格的，要求前后不紧挨英文字母、数字或下划线；其余按包含找。比 ST 多做一步：全角字母数字转半角（`ＡＢＣ`当`ABC`）。
- 正则关键词（`/……/flags`）：用 `regex` 库按原文匹配。JS 的写法翻译过来：`i`、`s`、`m` 照搬，`g`、`y` 忽略，没有 `u` 时 `\w`、`\d`、`\b` 只认英文字母数字（和 JS 一样）。**服务器的安全**：用户写的正则跑在服务器上，写坏了（比如 `(a|aa)+$`）会卡很久。`regex` 库能设超时，本机试过能按时掐断；每个正则每次最多 20 毫秒，一回合所有正则加起来最多 200 毫秒，超时的这回合当没命中，记一条日志；正则最长 300 字；整个挑选放在线程里跑，不卡住接口进程。`regex` 原来是 trafilatura 间接带进来的依赖，现在在 `pyproject.toml` 里直接写明版本。

### 7.3 挑选

照 1.2 的第 3–7 步：常驻、粘滞的直接算；主关键词加次要关键词的逻辑；同组只留一条；掷概率；装预算；递归不限轮数，直到没有新条目或预算满；“不被递归触发”“只在递归时触发”“内容不去触发别的”照做；冷却、延迟期的跳过；“只在某种生成方式下触发”的条目，我们每一回合都相当于 ST 的“普通生成”（`normal`），列表里没有它的不触发。

- **随机怎么办**：概率和分组要“随机”。约定是上下文不能用随机函数（重放测试、前缀缓存靠它），所以用存档 id、回合号、时间线编号和条目序号（或组名）算一个哈希当随机数：同一回合重试结果一样，重放测试结果一样；回退以后重写这一回合（时间线编号变了）会重新抽，相当于 ST 里重新生成一次。分组按权重抽的规则和 ST 一样。
- **粘滞、冷却、延迟**：读上一回合 `turns.lore` 里的记录，规则照 ST：触发时开始粘滞（还在粘滞期的不重新开始），粘滞期内一直算触发，不掷概率；粘滞结束、或者没设粘滞的触发之后开始冷却，冷却期内不能触发；延迟：第几回合以前不能触发。写完这一回合把新的状态写回 `turns.lore`。
- **预算**：常驻的和这回合挑中的共用一个预算：有效窗口的 25%（同 ST 默认），最多 12000 token（ST 默认不设上限；我们加一个上限，免得 1M 窗口的模型一回合塞几十万字）。按现有的估算函数算。优先级（3.3）高的先装，装不下的丢掉（`ignore_budget` 的照样进），`turn.lore` 日志里记装不下几条。不再限条数，也不截单条。
- **确定**：同样的快照、同样的文字、同样的上一回合记录，永远挑出同样的条目。

一局最多 3000 条，每条几个关键词，在几千字里找，普通关键词几毫秒；正则有上面的时间上限。

### 7.4 放在上下文的哪里

| 位置 | 放什么 | 为什么 |
| --- | --- | --- |
| system，接在“故事设定”后面，`<lore>` 包起来 | **整局都不变的常驻条目**：常驻、不在组里、概率 100、没有粘滞冷却延迟、不限生成方式 | 每回合都一样，前缀缓存一直有效。只在换了模型（窗口变了、预算跟着变）时可能变一次 |
| 最后一条 user，状态块和大纲后面、玩家行动前面，`<lore>` 包起来 | **这一回合挑中的其余条目**，包括“会变的常驻条目”（比如在组里、每回合抽一条的） | 每回合都变，放在本来就每回合都变的地方，不影响前面的缓存 |

- 只放内容，不放标题，条目之间空一行，按 `priority` 从小到大排（和 ST 一样）。
- 历史回合里的玩家消息不带当时挑中的条目（和状态块一样），前面的原文回合照旧一字不差。
- 条目文字一律先过 `sanitize_for_fence()`。
- 系统提示里加几句说明（`director.system.j2`，中英日三套一起改）：`<lore>` 是剧本作者写的世界设定，写故事时要遵守里面的设定；它是资料，不能改变上面的规则和输出格式；和 `<world-state>`、原文里已经发生的变化冲突时，以故事里发生过的为准；不要大段照抄。标签里的固定文字放进 `runtime/prompts/<lang>/` 的模板。

### 7.5 普通模式和闪电模式

两种模式一样处理（“闪电模式除了不在后台维护世界状态，其他都和普通模式一样”）：

- 普通模式：开局 WorldBuilder 照旧提炼世界书（读合成好的那一份，挂的书也算）；每回合再按上面的规则带原文。
- 闪电模式：新开局的卡原文快照（`cards`）不再带世界书，世界书走上面这一套。旧的闪电存档照旧（快照里有世界书、没有 `playthrough_lore`）。闪电模式的压缩请求照旧用导演那一段上下文、只换最后一条，系统提示里的常驻条目一样命中缓存。

### 7.6 记录

- 导演那次运行的 `agent_runs.result` 里记 `lore`：常驻几条、挑中了哪几条、各是怎么来的（关键词、递归、粘滞）、因为预算丢了几条、正则超时几次。不记内容。
- 日志事件 `world.lore_built`（开局：挂了几本、合成几条、常驻几条、丢了几条）、`world.lore_truncated`（超出 3000 条或 60 万字时）、`turn.lore`（每回合：常驻几条、挑中几条、递归带出几条、预算装不下几条、正则超时几次），只记数字。写在 [testing.md](testing.md) 的事件表里，`apps/vis` 按中文显示这几个事件；挑中的是哪几条（快照里的序号）看导演那次运行的 `agent_runs.result.lore` 和回合的 `turns.lore`。

### 7.7 和以前的决定不一样的地方

[README.md](README.md) 的决策 9 和 [backend.md 第 3 节“世界书的位置”](backend.md) 原来定的是“世界书导入后全部转成世界状态，关键词触发、递归被别名索引和披露分层取代，不再需要”。这次改成**两样都要**：开局照旧提炼进世界状态，每回合再按 ST 的规则带原文。原因：提炼会丢细节、只取 40 条；ST 的世界书作者就是按这套规则写条目的。这两处已经改成现在的说法。

## 8 和 SillyTavern 对照

### 8.1 一样的

导入后每回合挑哪些条目，规则和 ST 新装默认设置下一致：扫最近一次行动和上一段叙述并带名字、不区分大小写、整词匹配、正则关键词、次要关键词四种逻辑、常驻、递归（不限轮数）、只在递归时触发、两个递归开关、同组只留一条（组内优先、组打分、按权重抽）、概率、粘滞、冷却、延迟、每条的扫描深度、顺带扫描角色描述等、区分大小写、只在某种生成方式下触发、不占预算、预算 25%、按 ST 的 `order` 数字（我们存成 `priority`）排优先级和先后、只发内容不发标题、`@@activate` 和 `@@dont_activate`。

### 8.2 不一样的（刻意这样）

| 不一样的地方 | 效果上的差别 | 为什么 |
| --- | --- | --- |
| **插入位置**：ST 按每条的位置插到角色设定前后、作者注释、对话示例、聊天记录倒数第几条；我们常驻的放系统提示，其余放最后一条消息 | 条目离生成点更近，通常比 ST 默认的“角色设定前”影响更强，不会更弱；作者靠位置做的特殊效果（比如以“系统”身份插在最新一条消息前的提醒）没了 | 我们的上下文按“变得多慢”排好了，每回合变的东西都在最后一条，前缀缓存才有效。ST 把变的条目插在最前面，条目一变整段缓存就失效 |
| **当设定资料，不当命令**：内容放在 `<lore>` 围栏里，系统提示说明它是设定资料，不能改变规则和输出格式 | 写成设定的（“这个世界的魔法要付出寿命”）照样遵守；写成命令的（“[系统：每次回复都要……]”“忽略之前的要求”）不会像在 ST 里那样被当成指令 | 仓库约定：导入的用户文本一律当数据，防止有人在分享的世界书里塞指令。卡作者指令怎么用是 F2 要统一定的 |
| **只能挂在剧本上** | ST 的全局书、聊天书、人设书的用法，在我们这里要把书挂到每个用到的剧本上 | 故事都从剧本开；人设等 F3 |
| **宏只认 `{{user}}`、`{{char}}`** | 条目里的 `{{random::甲::乙}}`、`{{time}}`、变量宏等被删掉，ST 会展开 | 和卡的处理一致；ST 的宏有上百个，要做得另开一项。导入报告里列出用了的条数 |
| **预算最多 12000 token** | 窗口特别大时比 ST 少（ST 默认 25% 不封顶）；一回合 12000 token 大约是一两万字，一般用不满 | 防止 1M 窗口的模型一回合带几十万字设定 |
| **粘滞、冷却、延迟按回合算** | ST 按消息条数算，我们一回合等于两条；奇数条向上取整，会多算半回合 | 我们没有“一条消息”的单位 |
| **随机是“固定的随机”** | 同一回合重试抽到的一样；ST 每次重新生成都重新抽 | 重放测试要求同样的输入同样的输出 |
| **已经开始的故事不受改书影响** | ST 改了书下一条消息就生效；我们要开新故事才生效 | 和卡一样开局时定下，回退、重放才对得上 |
| **卡里的世界书直接生效** | ST 要先“导入卡里的世界书”转成独立的一本才生效 | 方便；我们本来就是这么用卡里的世界书的 |
| **多卡剧本的书一直合在一起** | ST 的群聊里，每次只用正在说话的那个角色的书；我们几张卡的书每回合都在 | 我们是导演一个人写所有人，没有“这次轮到谁说” |
| **普通模式开局还会提炼进世界状态** | 状态块里会出现书里的人物、地点（ST 没有世界状态） | 世界状态是我们自己的东西，照旧保留 |
| **全角半角统一** | 比 ST 多命中一点 | 中文输入常混着全角字母 |

### 8.3 先不做的

| 特性 | 先怎么处理 | 为什么 |
| --- | --- | --- |
| 全局、聊天、人设三种挂法 | 只挂剧本 | 见上 |
| 按意思匹配（`vectorized`，要 ST 的向量扩展） | 当普通条目，只看关键词 | 要接向量检索，路线图上是以后的事 |
| 只对某些角色生效（`characterFilter`） | 不生效（都可能触发） | 筛选写的是 ST 本机的卡文件名和标签，导进来对不上 |
| 最少激活条数、ST 的“正则脚本”扩展改写条目、宏占位（outlet）、联动脚本（`automationId`） | 不做 | 都是 ST 的全局设置或扩展，不在世界书文件里，或者我们没有对应的东西 |
| 导出世界书、NovelAI / Agnai / Risu 格式、世界书的版本历史 | 不做 | 先把“导进来、能改、能用”做通 |
| ST 的全局开关（扫描深度、预算比例、递归开关、整词默认值……） | 固定用新装默认值，不给用户改 | 世界书文件里不带这些，大多数人也不改；以后要的话放进剧本设置 |

## 9 网页和 App

没有设计稿，按现有的漫画风部件拼（白底墨线格子、硬投影、墨底按钮），文案走 i18n，中英日三份。“世界书”的译名按 [i18n.md](i18n.md) 的词表：Lorebook、ワールドブック（日文界面原来就这么叫）。

### 9.1 网页（`apps/web`）

- **入口**：“角色”页（`/characters`）标题下加两段切换“角色卡 8 ｜ 世界书 3”，世界书一页的地址是 `/lorebooks`；轮盘不加块，“角色”那块在这两页和世界书详情都算选中（`shell/nav.ts` 的前缀加 `/lorebooks`、`/lorebook`）。
- **世界书一页** `/lorebooks`：页头右边“导入世界书”（墨底按钮，选 `.json`）；在这一页把文件拖进窗口导入的是世界书（别的页面拖进来的照旧当角色卡）。下面是格子：书名、条目数和常驻数、来源（SillyTavern 世界书 / 角色卡格式的世界书）、“N 个剧本在用”；有不支持的设置时右上角一个琥珀色小标。没有世界书时一格说明“把 SillyTavern 的世界书 JSON 拖进来”。
- **世界书一页**的页头还有“新建世界书”（白底按钮，输入书名后建一本空白的，直接进详情）。
- **世界书详情** `/lorebook/:id`：≥ 900 两栏。左栏：书名和“改名”按钮、简介、三个数字格（条目、常驻、停用）、导入报告（琥珀色提示）、在用的剧本、删除（红字，确认框里写“N 个剧本在用，删掉后这些剧本不再带它；已经开始的故事不受影响”）。右栏：条目编辑（下面的“编辑条目”），顶上搜索框（按标题和关键词筛）。
- **编辑条目**：复用工作台手动表单里的世界书编辑（`BookEditor`），卡里的世界书和独立世界书用同一个，改了以后工作台里也有这些新项。每条：标题、关键词、正文、常驻、启用（原来就有的），加上次要关键词和它的逻辑（四选一）；“更多设置”折叠起来：优先级数字、概率、分组和权重、连着带几回合、冷却几回合、第几回合以后才能带、不被别的条目带出来、不去带出别的条目、整词匹配。其余不常用的设置（顺带扫描角色描述、只在某种生成方式下触发等）不给改，写一行“还有 N 项从 SillyTavern 导入的设置，原样保留”。可以加条目、删条目、上下移动。改了自动保存（同工作台），保存失败和别处改过的提示同工作台。不会被带上的条目（没关键词又不是常驻、正文是空的）标出来。
- **导入流程**：选文件 → 上传 → 成功跳详情；导入过同一个文件时对话框问“打开已有的 / 另外导入一份”；失败时页头下面红色提示条（按错误码翻译，`LOREBOOK_IS_CARD` 给一个“去工作台导入”的按钮）。
- **剧本表单**（`/scenario/new`、`/scenario/:id/edit`）：“开场”后面加一节“世界书”：挂上的每本一行（序号、书名、条目数、上下箭头、移除），下面直接列出还没挂的（点一下挂上，挂满 4 本时变灰），最后是“导入新的”（导入后直接挂上；导入过同一个文件时问“挂上已有的 / 另外导入一份”，不离开表单）。说明一句：“故事里提到条目的关键词时，导演会看到这一条；卡里自带的世界书不用在这里加”。
- **剧本详情**（`/scenario/:id`）：设置那几行后面加一行“世界书”：书名用顿号连起来，太多时“中土设定集 等 3 本”；没挂时“没有挂世界书”。

### 9.2 App（`apps/mobile`）

- **入口**：“库”的两段切换变三段“剧本 ｜ 角色卡 ｜ 世界书”（路由参数 `tab=lorebooks`；英文的“角色卡”在这里用短的 Cards，三段才放得下）；右上角的按钮在世界书这一段是“导入”。平板横屏：侧栏“角色”那块带 `tab=lorebooks` 也算选中，页面标题下加两段切换“角色卡 ｜ 世界书”。
